# 整合版下一轮的开源方法与实验建议

## 建议先做的实验

2026-11-18 在 Chrome 核对了参赛仓库、规则、PyTRiO Playground 和 SwanLab 工作区。远端与本地整合版均为 `df21cd2`。赛方页面列出平均提升、最差阶段与恢复速度、稳定性及资源效率四类客观评分。建议先从已有日志整理十轮公开表现，再决定哪种训练策略值得投入。[参赛分支](https://github.com/wurubin2-commits/-YSCG/tree/harness-integration-compact) · [赛方规则](https://rsi-index.115.zone/#rules)

1. **借鉴 River 的顺序评估。** 从本地 `rehearse.py` 的回执还原每轮父模型、候选、采用结果及耗时。比较同轮同验证投影上的两个版本，绘制分任务的逐轮主指标差。仅在存在可比的固定参照且有退化事件时统计恢复所需轮数，可见区间内未恢复须单列。竞赛训练与验证继续按 SDK 投影隔离。这里是本地分析方法，官方隐藏评分由宿主计算。[River 源码](https://github.com/online-ml/river/blob/main/river/evaluate/progressive_validation.py) · [BSD-3-Clause](https://github.com/online-ml/river/blob/main/LICENSE)
2. **借鉴 Transfer Learning Library 的 L2-SP，先试轴承 B。** 当前研究配方的普通 L2 惩罚权重大小。可另设一种 NumPy 配方，对权重相对当轮父检查点的位移施加惩罚。父权重须冻结。在一次梯度更新开始时两者相同，只有后续小批量更新才可能受影响。保留原优化器和预测接口，将强度和配方版本纳入去重记录。先用零强度核对标准训练等价，再固定一个非零强度与原版配对演练。若记录中没有足够更新步数，或结果不能复现，维持现有默认值。[SPRegularization 源码](https://github.com/thuml/Transfer-Learning-Library/blob/master/tllib/regularization/delta.py) · [论文](https://arxiv.org/abs/1802.01483) · [许可](https://github.com/thuml/Transfer-Learning-Library/blob/master/LICENSE)
3. **验收。** 本地对照锁定起点、数据顺序、种子、训练和调用预算。旧版复用已有证据，实验版先做 B 的配对对照。如初筛有收益，再在预先留出的公开批次或独立回放顺序复核。A 看 Macro-F1，B 看 RMSE 和 MAE（分钟），C 看 RMSE（循环）。每轮同时留存 SDK 回执、开销和决策理由。真实 Token、真实模型建议和隐藏成绩须在独立授权的真实环境核实。

## 备选的历史反馈与检查点选择

核查于 2026-11-18。对照参赛分支 `harness-integration-compact` 的 `df21cd2`、本机主办方 NumPy 基线和既有公开数据演练。本文只读源码与演练产物。下列改动属于建议，尚无新增训练、网关实测或比赛成绩。

**优先改历史反馈的可比性。** 分支已经向模型返回近期、成功和失败实验，已有重复实验拦截。可新增的最小功能是告诉模型哪些历史分数支持比较某个超参数，条件不足时只描述当轮结果。现有演练中所有可读取的标准候选逐 epoch 日志都只含一条记录。就这些产物而言，接入自动剪枝或恢复最佳 epoch 都没有可供选择的第二个点。[反馈实现](../../stage2_official/policy.py) · 演练产物（本地留档）

## 本地已经有什么

官方入口通过 SDK 恢复和保存 `rounds.json`，单轮向网关发起一次调用，输出上限取 192 与宿主上限中的较小者。训练动作为 1 或 2 个 epoch，最多提交一个候选。分支按每任务最多 12 个尝试 epoch 记账。父模型与候选按当轮公开指标比较，研究模式另检查保护切片。A 用 Macro-F1，B 用以分钟计的 RMSE，C 用以循环计的 RMSE。[官方入口](../../stage2_official/contest_submission.py) · [训练执行器](../../stage2_official/trainer.py)

`history_feedback()` 把至多三条记录分为同父同训练批、同父和更早三类，同时展示历史父分与候选分。其“同批”分类没有比较验证集摘要。精确去重则以任务、父检查点、训练摘要、种子和生效参数为键。只因验证摘要变化便放行相同训练，会重复构造相同检查点；因此验证摘要应参与**成绩解释**，原有训练去重键可继续使用。本地模拟策略也已有拒绝后降低学习率的规则。[反馈与去重](../../stage2_official/policy.py) · [模拟策略](../../stage2_local/planner.py)

只读统计了 `integration-normal-abc10` 各任务 10 份候选回执。每个任务分别有 10 个训练摘要、1 个验证摘要，A/B/C 各有 8/6/3 个父摘要。同任务内，父、训练、验证和种子全部匹配的重复组均为 0。因此这次演练无法分离学习率与训练批次的影响。另按 `runs/*/*/round-*/candidate/history.jsonl` 读取到 215 份候选日志，均为单 epoch；这一数量包含重复演练，也仅覆盖有该格式日志的候选。辨识覆盖范围时直接读取候选目录，未使用受限的临时工作目录。十轮对照目录（本地留档） · 演练目录（本地留档）

## 两个开源实现能借鉴什么

| 上游代码 | 源码行为 | 对本项目的判断 |
|---|---|---|
| Optuna 4.4.0 的 `TPESampler` | 默认累计 10 个已完成或已剪枝试验后才启用 TPE。此前由随机采样器给出独立参数。TPE 按目标排序并对较好和其余试验分别建模。 | 在上述每任务十轮演练中，就算忽略换批，默认配置也要到第 11 个试验才能利用历史分布。强行缩短启动期仍无法消除批次、父模型与参数共同变化的混杂。暂不引入运行时依赖。[固定版源码](https://github.com/optuna/optuna/blob/v4.4.0/optuna/samplers/_tpe/sampler.py) |
| Optuna 5.0.0 的 `PatientPruner` | 读取当前 trial 的中间分数。记录数小于或等于 `patience + 1` 时直接返回。 | 若每个 epoch 末上报一次，`patience=1` 到第 2 个 epoch 末仍不能剪枝；`patience=0` 最早可在第 2 个点作判断，此时本轮已结束。适合更长的训练轨迹。[固定版官方源码](https://optuna.readthedocs.io/en/v5.0.0/_modules/optuna/pruners/_patient.html) |
| scikit-learn 1.7.2 的 MLP 早停 | 从训练数据再划验证集。每个 epoch 用分类 accuracy 或回归 R² 计分，改进时复制系数与截距，训练结束时恢复这两组数组。 | 可借鉴逐 epoch 记录和选择。直接移植会改变数据划分、评分口径及检查点续训语义。当前体系已有公开验证投影。标准基线已按 epoch 评估并写入 `history.jsonl`，最后只保存末次模型。研究配方自身只报告训练前后。[上游实现](https://github.com/scikit-learn/scikit-learn/blob/1.7.2/sklearn/neural_network/_multilayer_perceptron.py) · A/C 基线训练逻辑（本地留档） · B 基线（本地留档） · [配方执行器](../../stage2_official/trainer.py) |

Optuna 4.4.0 采用 MIT，复制实质代码时应保留版权和许可声明。scikit-learn 1.7.2 采用 BSD-3-Clause，源码与二进制再分发各有声明保留要求，另有限制以作者名义背书的条款。下列建议可直接用当前 NumPy 模型和 SDK 实现。[Optuna 许可](https://github.com/optuna/optuna/blob/v4.4.0/LICENSE) · [scikit-learn 许可](https://github.com/scikit-learn/scikit-learn/blob/1.7.2/COPYING)

## 建议如何验证

1. **先让历史反馈明确证据范围。** 对同任务、父及训练摘要、验证摘要、种子、评估口径相同的已测记录，若两条记录还有且仅有一个生效超参数不同，可向模型提供该参数和两次有方向的收益差。一个候选需有可比较的父分与候选分；训练失败、缺失摘要及不可比分数只保留状态。若批次变化，可陈述该轮某配置是否被采用，但其数值不可作为调高或调低学习率的直接依据。成本是一轮内扫描少量 SDK 历史，复用现有模型调用。用保存的记录模拟“只换验证集”“只换父”“两个参数同时变化”“确实只换学习率”四种情况，验证前者不会产生归因，最后一种能够产生归因。[反馈实现](../../stage2_official/policy.py) · [参数与回执字段](../../stage2_official/contest_submission.py)
2. **需要选 1 或 2 个 epoch 时，先利用已经付过成本的轨迹。** 对未来标准配方的双 epoch 实验，可以从自己的 `trial/history.jsonl` 读取两个有限的公开验证指标，把第二个 epoch 相对第一个的方向写入 SDK 状态，供下一轮的唯一一次模型调用参考。缺少轨迹时省略该字段。该信号只描述对应的父、批次与配方。首要观测量是双 epoch 记录覆盖率、第二步改善比例及公开切片是否退化。现有 215 份日志对此没有覆盖。标准基线训练（本地留档） · [状态写入处](../../stage2_official/contest_submission.py)
3. **恢复最佳 epoch 放到覆盖率和收益都值得验证时。** 若主办方允许同一条训练轨迹在本地选择提交的 epoch，再做公开演练。使用同一份指定公开验证投影，在符合保护切片要求的点中按本任务方向选一个完整快照，再走原有平台比较与保留父模型流程。恢复第 1 个 epoch 时，必须同时恢复权重、偏置、Adam 一阶/二阶矩、步数、epoch、种子、归一化数组及完整元数据。训练过两个 epoch 就记两个，所选快照的步数和验证报告按实际快照填写，临时第二快照留在候选发布目录外。验收应比较从恢复的第 1 个 epoch 再续训一步与直接从原第 1 个 epoch 续训的参数和矩状态，并核对对外只登记一个候选。三任务的本机 `model.py` SHA-256 相同，项目原生 `save/load` 已支持上述字段。检查点保存和恢复（本地留档） · [预算与提交](../../stage2_official/contest_submission.py)
